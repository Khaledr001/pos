# Decisions

Settled questions. Each entry records what was chosen and why, so it does not
get relitigated in a later session. If a decision turns out to be wrong, add a
**Superseded** note rather than editing history.

---

## D1 — Multi-tenancy from day one, enforced by RLS

**Decided.** Every tenant-owned table carries `tenant_id`, and PostgreSQL
row-level security enforces isolation. Your business is tenant #1.

Two database roles:

| Role | RLS | Used by |
|---|---|---|
| `devsfleet_migrator` | bypassed (owner) | migrations, seed |
| `devsfleet_app` | **enforced** | everything at runtime |

The app role never owns tables. In PostgreSQL a table owner is exempt from its
own policies unless `FORCE ROW LEVEL SECURITY` is set, and depending on that
flag is one careless `ALTER TABLE` away from a silent cross-tenant leak.

Policies are generated by scanning `information_schema` for a `tenant_id`
column (`packages/db/sql/rls.sql`), so a new table is protected automatically.
`pnpm db:migrate` fails if any tenant-scoped table ends up without RLS.

Cost: roughly 10% extra complexity. Benefit: the platform is sellable to a
second business without a data-model rewrite.

## D2 — Drizzle ORM, not Prisma

**Decided.** The plan contradicted itself; the tech-stack table (Drizzle) wins,
and the folder layout was updated to match.

Reasoning: this schema leans on Postgres features Prisma cannot express without
dropping to raw SQL anyway — RLS policies, `TSVECTOR` generated columns,
`gin_trgm_ops` operator classes, partial unique indexes, and the immutability
triggers. With Drizzle those live in the same place as everything else.

Consequence: `packages/db-schema/prisma/` in the plan is `packages/db/` here,
and it holds the client as well as the schema.

## D3 — Electron + SQLite for the POS, not a PWA

**Decided.** Requirements were 58mm and 80mm thermal receipts *and* A4 tax
invoices, plus a cash drawer and a barcode scanner.

A PWA can only print through the browser dialog, which cannot cut paper, cannot
control column widths, and cannot fire the drawer kick pulse. IndexedDB is also
evictable by the OS under storage pressure — unacceptable for an outbox holding
a day's unsynced takings.

Cost: per-terminal install, ~150MB. Mitigated by `electron-updater` pointed at
the self-hosted VPS, so terminals update without a site visit.

## D4 — Meta Cloud API for WhatsApp

**Decided.** Direct, no per-message vendor fee, no lock-in.

Consequences already built in:
- Inbound webhooks must be verified with `X-Hub-Signature-256` against
  `WHATSAPP_APP_SECRET`. The env validator refuses to boot with WhatsApp
  enabled and that secret missing.
- Meta redelivers on any non-200, so `whatsapp_messages.wa_message_id` is
  unique — a redelivery cannot insert the message twice.
- The 24-hour customer service window is tracked on
  `whatsapp_conversations.window_expires_at`. Once closed, only an approved
  template may be sent; a free-form reply is rejected by the API.

## D5 — Money as scaled `bigint`, at DECIMAL(12,4)

**Decided.** All arithmetic is integer arithmetic in
`packages/shared-utils/src/money.ts`; conversion to `number` happens once, at
display. Numeric columns come back from Postgres as strings and stay strings.

Rounding is **half-up away from zero**, per line, at 2 decimals. Not banker's
rounding — it is not what a customer checking the receipt with a calculator
expects.

`calculateDocument` in `totals.ts` is the single implementation of line and
document totals, shared by the API, the POS and the admin panel. Two
implementations of the same tax maths will diverge, usually on the day a
customer notices.

## D6 — VAT is per-tenant configuration, not a constant

**Decided.** `tenants.settings.tax` holds `{ enabled, label, defaultRate, mode,
showBreakdown }`. UAE is 5% today, but the rate, the label and whether prices
are tax-inclusive all vary by tenant.

Each document snapshots its own `taxMode`, and each line its own `taxPercent`.
Restating a two-year-old invoice must not depend on today's settings.

## D7 — Multi-currency space reserved, AED in use

**Decided.** Every money document carries `currency` and `exchangeRate`
(snapshotted at issue). `tenants.settings.currency` holds `{ base, enabled,
decimals }`, and `ISO-4217` codes are already in `shared-types`.

Adding a second currency is then a data change and some UI, not a migration
across twenty tables.

## D8 — Credit is per customer, at the owner's discretion

**Decided.** Not tied to the wholesale flag. `customers.credit_limit`
(0 = cash only), `credit_balance`, `payment_term_days`, `credit_on_hold`.

`credit_balance` is a **cache** of `SUM(credit sales) - SUM(payments)`,
maintained in the same transaction as each. The reconciliation report recomputes
it from the underlying rows; if they disagree, the ledger wins.

Offline, a POS terminal accepts a sale that breaches the limit and raises a
`credit_exceeded` warning on sync — refusing it would mean a customer standing
at a counter that cannot see the server.

## D9 — Product images deduplicated by checksum

**Decided.** `product_images.checksum` is the SHA-256 of the uploaded bytes,
unique per tenant. On collision the API links the existing object instead of
uploading again.

Requirement was explicitly "no duplicate image is published". It also keeps
MinIO small across a catalogue where variants share photography.

## D10 — Languages: English, Arabic, Hindi/Urdu, Bangla

**Decided.** `LOCALES = ["en", "ar", "hi", "ur", "bn"]`; Arabic and Urdu are
right-to-left, so the admin panel's `<html dir>` must be dynamic.

Search consequence: `products.name_search` uses the `english` text-search
configuration (stems plurals, which suits most of this catalogue), while
non-English and misspelled input is served by a `pg_trgm` index on
`products.search_key`. One index cannot do both jobs.

## D11 — Gapless document numbers via a counter row

**Decided.** `document_sequences` plus the `next_document_number()` function,
not a PostgreSQL `SEQUENCE`.

Sequences are non-transactional: a rolled-back sale would permanently burn
`INV-2026-000042` and leave a hole in the invoice series. Tax authorities ask
about holes. The cost is that numbering serialises within one
(tenant, branch, kind, year) — at counter throughput, not a real constraint.

Numbers are labels, not identifiers. Every row has a UUID primary key, so the
POS can create a sale offline immediately and have the server assign the invoice
number on sync — no terminal ever invents a number another terminal might also
invent.

## D12 — Refresh tokens are rows, and rotate

**Decided.** Opaque random strings, stored SHA-256 hashed, rotated on every use.

Stateless JWTs cannot be revoked, and a lost terminal holds a 90-day token.
Presenting a token that was already rotated means it was captured, so the entire
token family for that user is revoked rather than just rejecting the request.

Access tokens are *not* checked against the database — a round-trip per request
(including per sync item) for a 15-minute token is cost without benefit.

## D13 — Express, not Fastify

**Decided.** Broadest ecosystem compatibility — multer for product image upload,
passport, `@nestjs/serve-static`. The bottleneck in this system is Postgres, not
HTTP parsing.

## D14 — Self-hosted VPS, `pos.devsfleet.com`

**Decided.** Postgres, Redis and MinIO via Docker Compose. Next.js builds with
`output: "standalone"` so the server bundle is self-contained. POS auto-updates
are served from `https://pos.devsfleet.com/releases`.

## D15 — A return is a linked negative sale, not a first-class document

**Decided**, going into Stage 2 (returns, voids, refunds — see feature.md).

A return is a new row in `sales`: `returnOfSaleId` points at the original,
its total is negative, and it is assigned its own `saleNumber` in the SAME
sequence as an ordinary sale (D11's gapless counter, not a second series). The
original sale's own `status` moves to `returned` or `partially_returned`, and
`saleItems.returnedQuantity` tracks how much of each line has come back —
supporting a partial return without a second table. A void is a separate
mechanism already: `voidedAt`/`voidedBy`/`voidReason` sit directly on the
sale being voided, no linked row involved, because a void means the document
should not have existed at all, where a return means it did.

Chosen over a first-class `sale_returns` table with its own number series and
per-line restock-vs-scrap disposition because the schema already commits to
this shape — `returnOfSaleId`, `returnedQuantity`, and a `SaleStatus` enum
that already distinguishes `returned`/`partially_returned`/`voided` were
shipped before Stage 2 was ever built against them. Building the alternative
would mean discarding real, already-migrated schema work and adding a second
number series with no user-facing requirement driving it.

**Open a new decision if UAE VAT credit-note numbering turns out to require a
distinguishable series** (a separate prefix/sequence a return document must
carry for FTA reporting) — that would favour the first-class-table design D15
rejected. Not confirmed either way at the time of this decision; revisit
before Stage 2 ships if it matters for this tenant's actual VAT reporting.
